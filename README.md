# Rocket Airbrake Controller Simulation

## Overview

This project is a Simulink-based 3DOF rocket flight simulation built to explore and compare different control theory approaches for active airbrake deployment during ascent. The goal of an airbrake system on a model/high-power rocket is to bleed off excess velocity during coast so the rocket reaches a target apogee as precisely as possible, rather than overshooting due to variable conditions (motor thrust variance, mass, weather, etc).

The simulation includes a **Physics subsystem** (motor force → drag → 3DOF body dynamics) feeding into a switchable controller block, allowing direct comparison between three distinct control strategies:

1. **Velocity Delta Controller** — compares live vehicle state against a pre-recorded open-loop reference flight profile
2. **PD Controller** — classic proportional-derivative feedback on velocity/altitude error
3. **Predictive Guidance Controller** — GNC-style forward prediction of apogee to drive airbrake deployment

Switching between strategies is done via a manual switch (SW1) so each can be evaluated independently against the same physics model.

## Focus of This Work: Velocity Delta Controller

Most of the recent effort went into refining the **Velocity Delta Controller**, specifically the core lookup function `findVelocityErrorAtAlt`, which is responsible for comparing the vehicle's current state against the reference flight profile at every control cycle.

The reference profile (`flightProfilePos`, `flightProfileVel`, `flightProfileAccel`) is generated by running the Physics subsystem open-loop (no airbrakes) and logging altitude, velocity, and acceleration over time. At runtime, the controller looks up "what should my velocity be at this altitude, according to the no-brakes reference?" and uses the difference (`deltaV`) to decide how much airbrake to command.

### Improvements Made

**1. Linear scan → Binary search**
The original lookup scanned the reference profile from the start every cycle to find the first index where the reference altitude reached the vehicle's current altitude. Since the reference profile is static and sorted (monotonically increasing altitude during ascent), this was replaced with a binary search for the same "first index ≥ target" condition, cutting lookup cost from O(n) to O(log n).

- Chose **binary search over a binary search tree** — a BST is designed for dynamic data with insertions/deletions; the reference profile is generated once and never changes, so a tree adds structural overhead with no benefit over searching a sorted array directly.
- Chose **iterative over recursive** binary search — avoids call-stack growth, and iterative loops are far more reliable for MATLAB Coder / embedded code generation, which matters if this ever gets deployed to real flight hardware.

**2. Linear interpolation → Cubic Hermite interpolation**
Originally, the function snapped to the nearest bracketing sample's velocity rather than accounting for where the vehicle's altitude actually fell between two logged points. This was upgraded to linear interpolation, and then further to **cubic Hermite interpolation**, which matches both the value *and* the slope (rate of change) at each bracketing point instead of assuming a straight line between them.

The slope of velocity with respect to altitude at each reference point is derived physically via the chain rule:

```
dv/dpos = (dv/dt) / (dpos/dt) = acceleration / velocity
```

This required adding `flightProfileAccel` as a new logged output from the Physics subsystem, so the reference profile carries acceleration data alongside position and velocity.

**3. Robustness fix**
The original implementation silently returned `deltaV = 0` if the vehicle's altitude exceeded every point in the reference profile (i.e. no match found), which could mask real errors. This was replaced with a defined fallback (extrapolate from the last known point) instead of a silent zero.

### Why These Changes, Not Just "Fancier Math"

Each change was made as a deliberate tradeoff, not applied by default:

- Binary search only helps if lookup cost actually matters relative to the rest of the control loop — for a reference profile with a few hundred to a couple thousand samples running at typical control rates, the linear scan likely wasn't the bottleneck to begin with (Simulink's own solver overhead dominates). The change was made for correctness of approach and scalability, not because it was measured as a bottleneck.
- Hermite interpolation is only worth the added complexity if the reference profile is sparsely sampled relative to how fast velocity actually changes. Since the profile is logged at high rate from an `ode45`-driven simulation, linear interpolation error was likely already small — Hermite was implemented to remove that assumption entirely rather than rely on "probably good enough" sampling density.
